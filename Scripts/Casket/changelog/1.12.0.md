# 1.12.0

- added: `settings security headerOffset enable|disable|state` and
  `headerEncryption enable|disable|state` — two independent, off-by-
  default toggles that hide a vault's LUKS2 header from magic-byte
  scanning and casual inspection. `headerOffset` relocates the header
  from its normal front-of-file position into a passphrase(+keyfile)-
  derived slot inside a new fixed 32 MiB room appended before the
  metadata trailer, scrubbing the front region to fresh random bytes.
  `headerEncryption` encrypts the header's content wherever it
  currently lives (front or relocated) under a key derived from the
  same secret material. Both derive from one shared KDF pipeline --
  Argon2id(salt, framed passphrase[+keyfile bytes]) for the slow,
  memory-hard master secret, then HKDF-Expand with a distinct purpose
  label per output (`"cas:header-slot"`, `"cas:header-key"`) -- so
  enabling one feature never leaks anything about the other's key
  material, and the framing is deliberately extensible to a future
  third secret input without restructuring. Enable/disable/rotate all
  follow one safety discipline: write the new header copy, verify it
  with a real detached-header open plus a payload checksum (a
  structurally-valid open with the wrong volume key still "succeeds"
  and just decrypts garbage), commit `Meta` to point at the new
  location, and only then scrub the old one -- so no crash window ever
  leaves a vault with no valid header anywhere. Passphrase rotation
  (`auth passwd`), 2FA enable/disable (`settings 2fa`), and keyfile
  regeneration (`auth keyfile reset`) all relocate the header
  automatically when the underlying secret material changes under
  either toggle.
- added: schema migration v4 -> v5 (`migrations/v5.rs`) -- `tamper::
  Protected` gained `header_room`/`header_offset`/`header_encryption`,
  so any existing `meta_hmac` baseline can never match post-upgrade
  regardless of tampering, same "drop it, fall back to Unprotected
  rather than a false Tampered" fix as v3/v4's identical field-shape
  problem. `tamper::reset_to_safe` re-derives `header_offset`/
  `header_encryption` from physical ground truth (does byte 0 have
  valid LUKS2 magic? does the room's active slot decrypt without a
  key?) rather than trusting or blindly resetting the stored booleans
  -- same approach already used for `file_integrity`.

Verified live: real scratch-vault checksums across every enable/
disable/rotate combination for both toggles independently and
together, plus every one of the user's 6 real production vaults in
`~/Images/` (1 GB to 251 GB) opened, migrated cleanly to schema v5,
and closed with no errors or data loss before this changelog was
written.
