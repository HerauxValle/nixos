# 1.10.19

- added: cgroup v2 resource limits for `exec` sessions --
  `src/sandbox/cgroup.rs`. `cas <vault> settings security sandbox
  cgroups set --mem <val> --cpu <percent> --pids <n> | clear | state`
  stores limits in Meta (`sandbox_cgroup_mem/cpu/pids` -- not
  tamper-HMAC-covered, same category as `backup_auto`/
  `backup_auto_keep`: resource management, not a protection toggle).
  `exec` applies whatever's configured fresh each session; unset means
  unlimited, same "absent = built-in default" shape every other
  sandbox setting already uses.
- added: `/sys/fs/cgroup/cas-exec/<vault>-<pid>` session directories,
  created and delegated (`memory`/`cpu`/`pids` controllers) on demand,
  removed automatically once the session ends -- nothing persists on
  the host between `exec` invocations, only the limit *configuration*
  lives in the vault's own trailer. `cas` already runs as real root
  (self-elevates via sudo, see `main.rs`), so this is a plain
  root-writes-to-sysfs operation -- the one place `exec`'s sandbox
  mechanics aren't unprivileged, matching the original design's
  explicit exception for cgroups (cgroupfs writes are real host-file
  permission checks, not namespaced, unlike everything else `exec`
  does).
- added: the session cgroup's `cgroup.procs` file is opened *before*
  `unshare`/`pivot_root` ever run (from the host side, in
  `commands::exec::dispatch`, ahead of `sandbox::run`) -- the PID1
  child writes its own pid through that already-open fd right after
  the required fork, before the foreground command. File descriptors
  stay valid across `pivot_root` regardless of mount namespace changes,
  the same trick every real container runtime uses for exactly this
  reason (a path-based join would fail once the host filesystem is
  unreachable post-pivot).
- fixed (caught before shipping, not a live regression): cleanup only
  ran after a successful fork+`waitpid`, so a session that failed
  *before* the fork (e.g. this dev box's already-documented
  pre-existing pivot_root/bind-mount limitation) leaked its cgroup
  directory. `cgroup::Handle` now cleans up via its own `Drop` impl
  instead of an explicit post-`waitpid` call, so every return path out
  of `sandbox::run` -- success or early failure -- removes the session
  directory. `std::process::exit` (what the PID1 child always uses
  instead of returning) skips destructors entirely, so only the
  supervising parent's `Handle` ever actually runs the cleanup, exactly
  once.

Verified live against a throwaway vault: `cgroups set --mem 64M --pids
32` produced a real cgroup with `memory.max=67108864` and `pids.max=32`
correctly delegated and written; a deliberately-forced early failure
(this dev box's known pre-fork limitation) confirmed the directory is
now removed regardless, where before this fix it was left behind. Full
namespace/pivot_root enforcement itself remains unverifiable in this
specific dev environment for the same pre-existing reason documented in
earlier slices.
