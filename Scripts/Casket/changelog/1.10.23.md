# 1.10.23

- fixed (CRITICAL, found by a functional QA subagent pass): `cas
  <vault> exec` failed unconditionally with `Permission denied (os
  error 13)` -- the entire sandbox/exec feature never actually worked.
  Root cause: `namespaces::Flags.user` was forced on and unshared
  *before* any of the mount setup (overlay mount, bind-mounting
  `new_root` onto itself for `pivot_root`), but `cas` already
  self-elevates to real root via `sudo` for every command -- and a
  newly created user namespace has zero capability over mounts owned
  by the real (init) namespace, no matter how its uid map is set
  (`cap_capable()` only grants capabilities *downward* into namespaces
  you create, never back up into the one you came from). So every
  mount operation the sandbox setup needed failed. Fixed by unsharing
  every other namespace first, performing all mounting/pivoting as
  real root (which already has every capability needed), and only
  entering the user namespace afterward, immediately before hardening
  and the fork into the actual sandboxed command -- preserving the
  intended unprivileged-command containment while no longer blocking
  the setup that has to happen before it. Verified live end-to-end: a
  statically linked binary placed inside a bare vault mount now
  actually executes inside a real `pivot_root`-isolated sandbox.
- fixed (CRITICAL, found by the same QA pass): `backup restore` always
  destroyed the vault's live contents and then failed. It creates a
  writable btrfs snapshot as its own separate subvolume, deletes every
  top-level item in the vault, then tried `std::fs::rename()` to move
  entries out of that snapshot into place -- but renaming across a
  btrfs subvolume boundary always fails with `EXDEV` ("Invalid
  cross-device link"), even though both subvolumes live on the same
  physical filesystem. This is a hard kernel limitation, not an
  environment quirk, so the old code path could never have succeeded.
  Fixed by using `cp --reflink=always` instead of `rename()` -- a real
  copy, so no `EXDEV`, but copy-on-write, so no meaningful time or
  space cost. Verified live: restore now correctly reverts a vault to
  its snapshotted state with no data loss.
- fixed (found by an adversarial CLI-breaking subagent pass): `cas ""
  delete` (an empty vault name) deleted its own containing directory.
  `Vault::mnt` is `base.join(name)`, and `PathBuf::join("")` is a
  no-op -- so with an empty name, `mnt` silently aliased `base` itself
  (the directory the vault lives in, or the cwd for a bare relative
  vault), and `delete`'s empty-mount-dir cleanup step then removed
  that real directory instead of a vault-specific one whenever it
  happened to be empty at the time. `Vault::resolve` now rejects
  empty, `.`, `..`, and separator-containing names outright.
- fixed (found by the same pass): `create` had no minimum vault size
  check -- `resize` already enforces a 96 MiB (`MIN_VAULT_MB`) floor,
  but `create` would happily produce a vault too small for
  `mkfs.btrfs` to ever format, discovered only at first `open` via a
  raw cryptsetup/mkfs error instead of a clean `cas`-level one. `create`
  now enforces the same floor.
- fixed (found by the same pass): vault `rename <newname>` and
  `backup create/restore/delete <name>` had no path-traversal
  protection on their name arguments -- `cas v rename ../escaped`
  actually moved the vault file out of its own directory, and `backup
  create "../../evil"` created an untracked btrfs subvolume outside
  `.casket/snapshots/`. New shared `src/name.rs` validator (same shape
  as `rootfs::validate_name` from 1.10.22) is now called by all three.
- fixed (found by the same pass): `settings security sandbox
  namespaces set ""` bypassed the "the `user` namespace can't be
  removed" protection that `namespaces disable user` already enforced
  -- `set` replaces the whole list outright and had no equivalent
  check, so it could silently store a namespace set that misrepresented
  reality (`exec` always forces `user` on regardless of stored state,
  so this was a metadata-consistency bug, not an actual exec-time
  bypass). `set` now refuses the same way `disable` does.
- fixed (found by the same pass): `rootfs add <name> --preset X
  --tarball Y` (both flags given together) silently mis-parsed instead
  of rejecting the conflict -- the parser treated the literal string
  `--tarball` as `--preset`'s positional `<version>` argument and
  dropped the actual tarball path, producing a confusing malformed
  fetch request instead of a clear error. Now rejected outright.

All seven fixes were found across three structured subagent passes (one
functional/intended-use QA pass, one adversarial CLI-breaking pass, one
aggressive pentest pass) run specifically to validate the 1.10.x
sandbox/namespace-isolation feature line before trusting it for real
use, rather than discovered in production. Every fix was reproduced
live against a throwaway vault before and after the change, and the
system was rebuilt and re-verified against the real installed `cas`
binary (not just a local build) before the pentest pass was considered
valid -- an initial pentest attempt correctly detected it was still
running against the pre-fix binary and refused to report against it.

The pentest pass found no exploitable vulnerabilities in the sandbox
isolation itself (pivot_root escape attempts, nested-namespace
unshare, in-sandbox mount attempts, and tamper-evidence bypass attempts
all failed as intended). It did surface one real design gap, documented
in `docs/known-issues.md` rather than fixed here: the sandbox's `net`
namespace isolation is an unbuilt stub (raw `unshare(CLONE_NEWNET)`
with no veth/loopback setup at all), so `exec`'s default of leaving the
network un-isolated exposes the real host network to sandboxed
processes, and simply flipping that default today would just break
networking outright rather than provide working isolated connectivity.
