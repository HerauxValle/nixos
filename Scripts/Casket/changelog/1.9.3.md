# 1.9.3

- fixed: resuming a `fileIntegrity` migration after it was killed
  mid-copy failed outright — `cryptsetup open` refused to re-open the
  staging container under a mapper name still held by the dead
  process's mapping ("Device ... already exists"), so a crashed
  migration couldn't be resumed at all despite the resume machinery
  existing. The staging container's mapper (and mount, if somehow still
  present) is now cleaned up before checking whether it's resumable,
  same as `open`'s own stale-mapper cleanup. Found via an actual
  kill -9-mid-migration test, not just re-reading the code.
