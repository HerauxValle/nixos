# 1.10.1

- fixed: tamper-evidence only covered `ransomwareProtection`/
  `verify_required`/`zeroize` — the 3 fields that existed when it was
  built. `bruteforceLockout` and `fileIntegrity` were added afterward
  and never got included, so someone with local read/write access to
  the `.img` file (no passphrase needed) could hand-edit the trailer to
  silently disable either one, bypassing `cas` entirely. Both are now
  covered. Verified live: hand-tampering `bruteforce_lockout` to
  `false` is now detected by `tampered`/`open`, same as the original 3
  fields always were.
- `bruteforceLockout`'s tamper-reset is the one field that doesn't
  follow "reset to the more-protective value" — forcing it *on* has a
  destructive, irreversible side effect (vault deletion after N wrong
  attempts) the owner never actually asked for if the trailer was
  tampered or just corrupted by a bug. It resets to *off* instead;
  losing a brute-force defense is recoverable, an unwanted vault
  deletion isn't.
- `fileIntegrity`'s tamper-reset checks the real container via
  `cryptsetup luksDump` rather than blindly setting `true` — that field
  only describes what the container already is, so a blind reset could
  make `info` claim a protection that was never actually there.
