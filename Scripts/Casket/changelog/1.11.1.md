# 1.11.1

- fixed (found by a QA subagent pass feature-testing the new named
  custom seccomp profiles): `cas`'s self-elevation re-exec via `sudo`
  (`main.rs::elevate`) didn't preserve `$EDITOR`, since plain `sudo`
  resets the environment by default -- silently dropping a user's
  editor choice before `seccomp custom edit <name>` (or any future
  command that shells out to `$EDITOR`) ever saw it, launching root's
  own default editor instead with no explanation. Now passes
  `--preserve-env=EDITOR` specifically (not a blanket `-E`) through the
  re-exec. Note for anyone re-verifying this on a system with a
  system-wide forced `$EDITOR` default (e.g. NixOS's
  `environment.variables.EDITOR`, sourced via `/etc/set-environment`
  through PAM *after* sudo's own env handling): that kind of override
  wins regardless of this fix, since it happens downstream of sudo
  entirely -- not something any sudo flag can prevent. This fix is
  still correct and is the standard idiom for the general case.
- fixed (found by the same QA pass): a custom seccomp profile with
  `default = "deny"` that didn't also explicitly allow `getpid`/
  `wait4`/`kill`/`fork`/`clone`/`exit_group` made `exec` fail entirely
  with a confusing, non-seccomp-branded error (`refusing to run as
  PID1 reaper: own pid is -1, not 1`) -- because those syscalls aren't
  just what the *command being run* might need, they're what `exec`'s
  own PID1 supervisor (`sandbox::reaper::run_as_pid1`) needs for its
  own bookkeeping, and a strict default-deny profile blocks those too.
  `-1` specifically (not just "not 1") now gets its own clear message
  pointing at the actual cause and which syscalls to add. `seccomp
  custom create`/`edit <name> default deny` also now print a proactive
  warning about this requirement at the point a profile becomes
  default-deny, rather than only after the fact.
- fixed (found by the same QA pass): once any rootfs environment
  existed, there was no way to reach the vault's own root as a
  `seccomp`/`exec` target anymore -- unqualified `--rootfs`-less calls
  auto-select the sole environment (existing, intentional behavior for
  the common "I only have one environment" case), and `--rootfs _root`/
  `--rootfs ""` both failed since `_root` was never a real environment
  name. `_root` is now a proper sentinel, reserved in `rootfs::
  RESERVED_NAMES` and short-circuited at the top of the shared
  `rootfs::resolve()` (used by both `exec --rootfs` and `seccomp
  --rootfs`) to always mean "the vault's own content, not any
  environment" -- reachable now regardless of how many real
  environments exist.
- fixed (found by a pentest subagent review in 1.10.22, deferred and
  documented in `docs/known-issues.md` until now): `rootfs add
  <name> --tarball <path>`/`update --tarball` never validated symlink
  *targets* inside the archive being extracted -- only that the archive
  itself was well-formed (`tar -tf`). A symlink member pointing outside
  `base/` (an absolute target like `-> /tmp`, or a relative target that
  `..`s its way past the archive's own root) extracted successfully
  with no complaint. `extract_tarball_into` now runs `tar -tvf` before
  extraction, identifies every symlink member, and rejects the whole
  archive if any symlink's target is absolute or resolves -- lexically,
  against the member's own location, since the target doesn't exist yet
  at validation time -- outside the archive's own root. In-bounds
  relative symlinks (Alpine/Debian's `/bin -> usr/bin` shape, which real
  distro rootfs tarballs use structurally) still extract fine; only
  symlinks that actually escape are refused. Verified live: a
  hand-built tarball with an absolute-target symlink was rejected, one
  with a `..`-chained relative escape was rejected, and a real
  in-bounds relative symlink extracted normally.
