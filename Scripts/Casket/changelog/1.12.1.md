# 1.12.1

- fixed (CRITICAL, confirmed live to delete a vault using its own
  *correct* password): `bruteforceLockout` + `headerOffset` together
  made `check_lockout` (`commands/open.rs`) misread every correct
  password as wrong, because it tested the passphrase with plain
  `luks::test` against the front of the file -- which, once
  `headerOffset` is enabled, holds freshly-scrubbed random bytes, not
  a header. Now uses `header::relocate::verify_current_secret`, which
  checks wherever the header actually lives.
- fixed (CRITICAL, confirmed live): a single wrong/mistyped password
  against a `headerOffset`/`headerEncryption` vault silently corrupted
  the `header_offset`/`header_encryption` trailer fields. `tamper::
  verify`'s HMAC is keyed by whatever secret was typed, so a wrong
  password is indistinguishable from real tampering; `check_tamper`
  reacted by calling `reset_to_safe` with that *wrong* secret, which
  couldn't prove anything and fell back to "native front, unencrypted"
  -- and that bogus value got persisted even though the open then
  failed, bricking the *next* open until an incidental self-heal.
  `check_tamper` now verifies the secret first and does nothing if it
  doesn't check out, rather than concluding anything from a mismatch it
  can't trust.

Both found live via a targeted CLI-misuse pass on the two new toggles
added in 1.12.0, before either bug could reach real vaults.
