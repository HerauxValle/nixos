# 1.10.21

- fixed (security, found by QA subagent review): `rootfs add/update/
  remove/rename/default` never called `gate_inner` -- every other
  sandbox mutation (`enable`/`disable`/`namespaces set`/`seccomp set`/
  `cgroups set`) requires re-proving the vault's real passphrase before
  writing (per `verify_required`, on by default for the `sandbox`
  feature), but the five files under `commands/settings/security/
  sandbox/rootfs/` never threaded the `pw` parameter through at all --
  `rootfs::dispatch`'s own signature took an unused `_pw: Option<&str>`.
  Since `rootfs::default_target`'s own doc comment already calls the
  `default` symlink "plain user/attacker-writable filesystem state
  feeding directly into what `exec` later pivot_roots into," this meant
  anyone with filesystem access but not the passphrase could add,
  replace, rename, or re-point the default of a rootfs environment a
  later `exec` would pivot into, without ever passing the verification
  gate the rest of the feature enforces. `pw` is now threaded through
  `rootfs::dispatch` and every mutating leaf (`add`, `update`, `remove`,
  `rename`, `default set/clear` -- `default`'s read-only `show` and
  `list` remain ungated, matching every other read-only state command).
  `sandbox disable --removeRootfs` reuses the passphrase already
  resolved by its own earlier `gate_inner` call instead of prompting
  twice.
- fixed (found by QA subagent review): `seccomp set custom` reported
  success even when the custom syscall list was never actually
  authored -- `edit custom` pre-creates a placeholder file *before* the
  editor runs and only records a hash *after* a successful editor exit,
  but `set custom` only checked the placeholder file's mere existence,
  not whether a hash was ever stored for it. A cancelled or failed edit
  left a file on disk with no matching hash, and `set custom` would
  still print `[✓] seccomp set to 'custom'` -- misleading, though safe
  in practice since `exec`'s own `resolve_seccomp` already detects the
  missing hash and falls back to `strict`. `set` now checks for a
  stored hash (the same signal `resolve_seccomp` checks), matching
  reality instead of file presence.

Both fixes found during a structured QA pass (functional-testing
subagent, phase 1 of 2) rather than live production use. Verified live
against a throwaway vault: `rootfs add` now correctly refuses with a
wrong passphrase (previously succeeded unconditionally with none
prompted at all); `seccomp set custom` now correctly refuses before any
`edit custom` has ever completed successfully for that target.
