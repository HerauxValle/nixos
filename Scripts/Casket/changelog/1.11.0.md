# 1.11.0

- added: named, reusable custom seccomp profiles --
  `settings security sandbox seccomp custom list|create|delete|rename|
  edit <name>`. Replaces the old single unnamed custom syscall list per
  target (which could only ever be a plain allowlist) with a vault-wide
  registry of named profiles, stored as TOML under `.seccomp.d/`, any
  of which can be assigned to any target via the same flat `seccomp set
  <name>` built-in presets use -- no prefix needed, built-ins and
  custom profiles share one namespace (`profiles::create`/`rename`
  refuse any name that collides with a built-in, so the two can never
  actually clash). A profile can be reused across multiple rootfs
  environments or the vault's own root target at once. Custom profiles
  can be edited/deleted/renamed via `seccomp custom ...`; built-ins
  can't -- they're compiled into the binary, not real files.
  - `seccomp custom edit <name>` with no further arguments opens
    `$EDITOR` on the profile's raw TOML, same as before.
  - `seccomp custom edit <name> add [--allow <list>] [--deny <list>]`
    and the matching `remove` add/remove syscalls without opening an
    editor -- `--allow`/`--deny` can appear in either order, each
    scopes the comma-separated list that immediately follows it, and a
    bare list with neither flag is treated as `--allow` (matching the
    old allowlist-only behavior for the common single-list case).
    Entries can be given as syscall names or numeric ids -- an id is
    auto-resolved to its canonical name for the host's architecture
    before being written, so the file on disk always stores names.
  - A profile can now define an allow list *and* a deny list at once,
    plus an explicit `default <allow|deny>` fallback for anything named
    in neither -- the old feature could only ever express "allow only
    these", never a genuine mixed allow+deny policy. A syscall named in
    both lists is rejected outright rather than silently letting one
    win.
  - `seccomp custom status <name>` shows a profile's default action and
    full allow/deny lists, or a clear "doesn't exist" message.
  - `seccomp custom delete <name>` refuses if any target still
    references the profile; `rename` carries every referencing target's
    pointer forward automatically.
- changed: `sandbox::seccomp::apply`'s underlying BPF filter builder now
  takes an explicit `Filter { default_deny, allow, deny }` instead of a
  single `Mode` + one syscall list -- the mechanism was already just a
  linear "check syscall, return an action" chain per entry, so
  supporting both lists at once (deny checked first, so an explicit
  deny always wins if a syscall somehow ended up in both) needed no
  new capability, just a richer shape for what was already there.
  Built-in presets (`default`/`strict`/`compute`/`none`) are unaffected
  -- they still resolve to the equivalent single-list form under the
  hood.
- added: schema migration v2 -> v3 (`migrations/v3.rs`). Converts each
  target's old bare `"custom"` seccomp setting into the target's own
  key (which becomes the new profile's name in the shared flat
  namespace, preserving which target used which list), and converts
  each old plain-text `.casket-seccomp` file into the equivalent TOML
  profile under the vault's new `.seccomp.d/`. Also drops the stale
  tamper HMAC
  baseline for any vault this migration actually touches -- the HMAC
  is computed over the field shape at write time, so a legitimately-set
  HMAC from before this migration can never match the post-migration
  shape; clearing it (falling back to "no baseline yet" rather than a
  false "tampered") avoids `open` incorrectly triggering
  `reset_to_safe` on every single open after upgrading, over a schema
  change rather than an actual attack. Verified live: a hand-crafted
  v2-shaped vault with a real custom seccomp list migrated cleanly with
  no false tamper report, correct file conversion, and the old file
  removed.

Not fixed, deliberately out of scope (found live while verifying this
feature, reproduces identically with the plain built-in `strict` preset
on its own, unrelated to anything added here): running a statically
linked binary under `exec` with `strict` active segfaults instead of
running normally. Documented in `docs/known-issues.md` rather than
chased down mid-feature -- root-causing needs its own focused pass to
bisect which syscall `strict`'s allowlist is missing.
