# 1.10.22

- fixed (CRITICAL, found independently by both the QA and pentest
  subagents): rootfs environment names went straight into
  `dir.join(name)` with zero path validation across every mutating
  command (`add`, `update`, `remove`, `rename`, `default`) and the
  shared `resolve()` used by `exec --rootfs`/`seccomp --rootfs`. A name
  containing `/` (relative traversal like `../../etc`, or a full
  absolute path like `/tmp/evil` -- `PathBuf::join` replaces the base
  entirely for an absolute argument, per Rust's own documented
  semantics) reached real filesystem writes at an arbitrary host path,
  including a root-privileged recursive `chown` (`cas` self-elevates).
  Confirmed live by both subagents independently. New
  `rootfs::validate_name` (no `/`, `\`, null bytes, empty, or bare `.`/
  `..`) is now called at every one of those six call sites before any
  name is ever joined onto a directory path -- the first line of
  defense a path-traversal bug like this needs, applied everywhere the
  bug was reachable, not just the one entry point that got tested.
- fixed (MEDIUM, found by the pentest subagent): the tamper-evidence
  HMAC over `sandbox_enabled`/`sandbox_namespaces`/`sandbox_seccomp`
  was computed and checked by `open`/`info --pass`/`tampered`, but
  never by `exec` itself. `exec` already resolves the vault's real
  secret via `gate_inner` (verification is on for `sandbox` by
  default) -- it just never used that secret to check the tag before
  trusting the fields it read. A vault left open, then had its trailer
  hand-edited on disk (narrowing `sandbox_namespaces`, weakening
  `sandbox_seccomp`) without a fresh `open` in between, would have
  `exec` silently apply the tampered config with no warning, even
  though `open`'s own tamper check (which only runs at open time)
  would have caught the same edit had a fresh `open` happened instead.
  `exec` now checks `tamper::verify` against that already-resolved
  secret and refuses outright on a mismatch, rather than silently
  proceeding.
- fixed (MEDIUM, found by the QA subagent): `cgroups set --pids 0`,
  `--cpu 0`, and `--mem 0` all previously succeeded with no bounds
  check -- each would make every subsequent `exec` session unusable
  (a 0 pid cap means the kernel refuses to fork/exec anything at all;
  0 CPU/memory are equally self-defeating), silently, with no warning
  at set time. All three are now refused with a clear explanation.
  `--cpu` above 100 remains allowed (legitimate on a multi-core host,
  e.g. 400 = up to 4 cores).
- fixed (LOW, found by the pentest subagent): `sandbox::cgroup::
  parse_bytes` did an unchecked `n * mult` -- an absurdly large value
  (e.g. `18446744073709551615g`) silently wrapped instead of being
  rejected. Now uses `checked_mul`, correctly refused by the existing
  invalid-value error path instead of wrapping.

Not fixed, deliberately deferred (LOW, found by the QA subagent):
tarball extraction (`rootfs add/update --tarball`) doesn't validate
symlink *targets* inside the archive -- a symlink member pointing
outside `base/` (e.g. at `/tmp`) extracts successfully. `..`-containing
member *names* are already blocked, but only incidentally (GNU `tar`
itself refuses those, not a check `cas` performs). Assessed as
contained today (namespace/pivot_root isolation means the symlink is
largely inert even where it points), but a real fix needs to inspect
`tar -tvf` member types and resolve symlink targets against `base_dir`
-- outright banning all symlinks would break legitimate distro rootfs
tarballs that use them structurally (e.g. Alpine/Debian's `/bin ->
usr/bin`). Left as a known gap rather than shipping a rushed fix that
could break the common case; worth a dedicated pass later.

Every fix in this release was found by two 20-minute subagent reviews
(one functional/adversarial QA pass, one aggressive pentest pass) run
against v1.10.20/1.10.21 rather than discovered in production use, and
each was independently reproduced against a throwaway vault before and
after the fix to confirm both the bug and the correction.
