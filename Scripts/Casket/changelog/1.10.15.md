# 1.10.15

- added: `backup rootfs include|exclude <name>|all | state` — opt named
  rootfs environments into `backup create`/the auto-backup rotation.
  Default: none included. `.casket/` has no equivalent flag — never
  includable.
- fixed: brand-new vaults never got `.casket/` created as a real
  subvolume at all (only the v2 schema migration handled converting an
  *existing* plain-directory `.casket/`) — silently defeating the "a
  snapshot never includes `.casket/`" guarantee for any vault created
  after the sandbox feature shipped. Fixed at the same place `.casket/`
  first gets created (first backup).
- fixed: included-rootfs copies originally targeted `dest/.rootfs.d/
  <name>` inside a snapshot — but that exact path is where the vault's
  own `.rootfs.d` subvolume boundary used to be, and btrfs keeps it as
  a protected placeholder even after snapshotting (`mkdir` there fails
  `EPERM`, even as root). Moved to a non-colliding path
  (`.casket-included-rootfs/<name>`).
- fixed: a snapshot is now taken read-write, populated with included
  rootfs copies, then flipped read-only — taking it read-only from the
  start (the original order) would have refused the population step
  entirely.
- fixed: individual `.rootfs.d/<name>/` directories aren't themselves
  btrfs subvolumes (only `.rootfs.d/` as a whole is), so `btrfs
  subvolume snapshot` can't target one directly — switched to a
  reflink copy (`cp -a --reflink=auto`), still cheap CoW on btrfs.

Verified live against a throwaway vault: included one of two rootfs
environments, ran `backup create`, confirmed only the included one
appears (under the new path), the vault's own `.rootfs.d/` stays empty
in the snapshot, and a brand-new vault's first backup now creates
`.casket/` as a real subvolume from the start.
