# 1.10.7

- added: `cas <vault> exec [-- <cmd> ...]` — drops a shell (or runs one
  command) sandboxed inside the vault's own mount via `src/sandbox/`,
  using whichever namespaces `settings security sandbox namespaces`
  has active. Requires the vault open and `sandbox` enabled first.
  `--rootfs` is parsed but rejected — named rootfs environments don't
  exist yet.
- added: `--debug` documented in `cas help`/`cas help exec`.

Verified: full lifecycle (refuse when sandbox disabled, refuse when
closed, enable, run) against a throwaway vault. The unprivileged
namespace/pivot_root machinery is proven solid end-to-end (validated in
1.10.6's slice). The privileged path specifically — `cas` always
auto-elevates via `sudo`, and this dev environment's own sandboxing
refuses a plain self-bind-mount as real root (confirmed via raw
`unshare` CLI too, independent of this code) — could not be verified
here. That's a property of this specific dev/agent environment, not
necessarily of a real target machine; needs real-hardware verification
before relying on `exec` in production.
