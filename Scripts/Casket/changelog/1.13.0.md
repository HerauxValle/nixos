# 1.13.0

- added: `headerOffset`/`headerEncryption` now work on `fileIntegrity`
  vaults. The 1.12.5 mutual-exclusion guard is gone in the
  `headerOffset`/`headerEncryption`-enable direction (`fileIntegrity
  enable` still refuses while either is on -- enable integrity first,
  then header-hiding). Mechanism differs from the non-integrity path:
  the real, full-size header is copied and rekeyed in place (never
  rebuilt via `luksFormat`, which is what corrupts an integrity
  container's payload) into a dedicated room -- see `--slots` below.
- added: `settings security headerOffset enable [--slots N]` and
  `settings security headerOffset slots <N>` -- slot count for a
  `fileIntegrity`-compatible room, defaulting deterministically by
  vault size (4 above 1 GiB, 2 below). Slot count is a disk-overhead
  knob, not a security one, past a handful (advisory printed above 8) --
  `derive_slot_index` is a public function of the passphrase guess, so
  an attacker checks exactly one slot per guess regardless of how many
  exist.
- changed: a `fileIntegrity`-compatible header room now lives in a
  dedicated sibling file (`.<vault>.hroom`) instead of being appended to
  the vault image -- required because the image's LUKS2 data segment is
  "till end of device" dynamic (never given a fixed size), so anything
  appended after it corrupts dm-integrity's tag/data layout the moment
  the header is rebuilt or even just reactivated. A non-integrity room
  is unaffected (still appended to the image) since a plain LUKS2
  payload has no size-dependent internal structure.
- fixed: `settings security headerOffset slots <N>` and passphrase
  rotation on a `fileIntegrity`-compatible room now use `luksChangeKey`/
  a verbatim byte copy instead of rebuilding the header, matching the
  same no-`luksFormat` discipline as enable/disable.
