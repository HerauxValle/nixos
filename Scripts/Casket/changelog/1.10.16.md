# 1.10.16

- added: `src/registry/seccomp.rs` — parses `data/seccomp-presets.toml`
  (default/strict/compute/none; `custom` has no registry entry, it's
  per-rootfs user data). Syscalls listed by name only, never numeric —
  resolved per-architecture at enforcement time (next slice). `compute`
  derives from `strict` minus networking syscalls.
- added: `settings security sandbox seccomp [--rootfs <name>] set
  <preset>|edit <preset>|state` — per-rootfs (or the zero-rootfs `_root`
  case) seccomp preset selection, using the same `--rootfs` resolution
  rule as `exec`. `edit` only works for `custom` (opens `$EDITOR` on
  `.casket-seccomp`, hashes the result into
  `sandbox_seccomp_custom_hash`); other presets refuse with a clear
  message. `set custom` refuses until `edit custom` has created the
  file at least once.
- refactored: `exec`'s `--rootfs` resolution logic moved from
  `commands::exec` into `rootfs::resolve`, so `seccomp` (and anything
  else later) shares the exact same rule instead of a second copy.

Enforcement doesn't exist yet — presets are stored but not applied to
`exec` sessions (next slice). Verified live against a throwaway vault:
default state, `set strict`/`state` round-trip, `edit` refusal on
built-in presets, `set custom` refusal before any custom file exists,
successful `set custom` once the placeholder file is created, tamper
check stays healthy throughout. The interactive `$EDITOR` spawn itself
wasn't exercised end-to-end here (this environment's `sudo`/env
propagation made a clean non-interactive test awkward) — the
surrounding logic (refusal conditions, gating, hash write) is otherwise
fully verified.
