# 1.17.0

- Fixed: `settings security bruteforceLockout` misclassified LUKS
  header/room corruption (bitrot, a bad sector, a torn write) as a
  wrong passphrase, counting it toward the deletion threshold and
  reporting it as "wrong passphrase" — meaning a few corrupted bytes
  near the header could get a vault auto-deleted with zero attacker
  involvement and the correct passphrase supplied every time. `open`
  now keeps a checksum baseline of the header (native-front) or the
  active room slot (headerOffset/headerEncryption) and only counts a
  failed open toward the lockout threshold when the header/slot is
  byte-identical to the last confirmed-good state; a mismatch now
  surfaces an honest corruption message pointing at `cas <vault>
  tampered` instead. Vaults that already had bruteforceLockout enabled
  before this update should re-run `settings security bruteforceLockout
  enable` once after upgrading, to seed the new baseline — until then,
  the very first post-upgrade check on such a vault falls back to the
  old behavior.
- Fixed: `settings security sandbox enable/disable/state` was real,
  working dispatch with no representation in `cli/registry.kdl` — it
  never showed up in `cas help settings security sandbox` or `cas debug
  parse-cli`, making the entire `exec` sandbox feature unreachable by
  anyone who only reads `cas help`. Now fully registered with its own
  ids and help text.
- Fixed: `cas help <topic> <bogus-trailing-tokens>` (e.g. `cas help
  settings totallybogus`) silently dumped the entire topic's help text
  instead of erroring, for any topic not fully expressed in
  `cli_registry` (settings, auth, backup). Now reports "no help topic"
  the same way an unresolved registry path already does; bare
  single-token topic names are unaffected.
- Fixed: vault, rootfs environment, backup snapshot, and custom
  seccomp-profile names only rejected filesystem-dangerous characters
  (`/`, `\`, NUL, `.`/`..`), accepting backticks, quotes, `$()`, `;`,
  `|`, and other shell metacharacters into on-disk filenames. `cas`
  itself was never exploitable through this (every subprocess call uses
  argv arrays, never a shell), but a maliciously-named vault was a
  landmine for any external wrapper script that naively interpolates a
  name into a shell command. Names are now restricted to an explicit
  allow-list: letters, digits, `-`, `_`, `.` (no leading/trailing `.`).
- Fixed: `<vault> info`/`list` reported raw on-disk file size (which
  includes a fixed 128 MiB reserve for the headerOffset feature) as
  plain `size`, with no indication a `create --size 200` vault would
  show 328 MiB later. `info` now shows usable size as the primary
  `size`, with on-disk size as a clearly labeled secondary line.
- Fixed (data corruption): `<vault> resize <size>` shrinking a vault
  computed the new btrfs/LUKS payload size without accounting for the
  full 128 MiB header-offset reserve, requesting a mapped size larger
  than what the truncated file actually held — the vault would report
  a successful shrink and then fail to mount at all ("wrong fs type,
  bad option, bad superblock"), a real, silent way to lose an entire
  vault's contents via ordinary use of a documented command. Shrink
  math and both size floors (the absolute minimum and the used-data
  safety floor) now correctly account for the reserve.
- Fixed: the vault size floor (`create --size` and `resize`) allowed
  sizes down to 96 MiB usable, but btrfs's own minimum formattable size
  is ~109 MiB — a vault created or shrunk to exactly cas's own reported
  "minimum" failed on first format/open with an `mkfs.btrfs` error. The
  usable floor is now 128 MiB, with matching on-disk floors in both
  `create` and `resize`.
- Fixed: `<vault> exec` under a custom seccomp profile whose allow-list
  didn't cover the sandbox's own supervisor syscalls (`getpid`, `wait4`,
  `kill`, `fork`, `write`, ...) — exactly the misconfiguration `seccomp
  custom create` itself warns about — failed completely silently: exit
  code 1, zero error text, actually an infinite signal-handling loop
  under the hood (the filter was blocking the supervisor's own error-
  reporting `write()` calls). The seccomp filter is now applied only to
  the final user command (right before it runs), never to the sandbox's
  own bookkeeping process, so a misconfigured profile now fails with a
  clear, actionable message instead of silence. Real enforcement against
  the user's command is unaffected — confirmed a profile that still
  denies e.g. `unshare` continues to block it.
- Fixed: `settings security sandbox network inbound add`/`enable`
  reported success and `exec` claimed "inbound forwarding active", but
  no traffic ever actually reached the forwarded port from the host —
  confirmed via loopback, the host's real interface address, and ruled
  out via a control test against the sandbox's own veth address (which
  worked, but only because of ordinary IP forwarding, unrelated to this
  feature). Root cause: the DNAT rule only existed on the `PREROUTING`
  netfilter chain, but locally-originated traffic (from the host itself)
  never traverses `PREROUTING` — only `OUTPUT`. Loopback specifically
  also needed `route_localnet`/`accept_local` sysctls on both veth ends
  plus a narrow hairpin `MASQUERADE` rule to get a reply back. Inbound
  forwarding now installs matching DNAT rules on both chains plus the
  loopback-hairpin setup; verified working via both loopback and the
  real interface address, with multiple concurrent forwarded ports, and
  with no regression to outbound connectivity or the loopback-only
  default when neither outbound nor inbound is enabled.
