# 1.9.4

Three bugs found by an adversarial testing pass (exploiter/naive-user/
general-user angles) over 1.9.0-1.9.3's security features, all fixed
and re-verified:

- fixed: after `open` auto-detected tampered metadata and reset the 3
  protected fields to their safe values, it never refreshed the HMAC
  baseline over those new (legitimate) values — so `tampered`/`info
  --pass` reported `Tampered` forever afterward, even though the fix
  had already been applied. A real tamper event became indistinguishable
  from this permanent false alarm. `check_tamper` in `open.rs` now
  calls `tamper::refresh` right after `reset_to_safe`.
- fixed: resuming a `fileIntegrity` migration after the vault was
  resized (interrupted, then `resize`'d, then re-run) got stuck in an
  endless "not enough room" loop with an ever-growing but never-correct
  suggested size — the resume path reused the staging container's
  original size unconditionally, which can never fit a vault that's
  since grown. Resume now checks the staging container's size against
  the vault's current size and discards+restarts fresh on a mismatch,
  instead of trying to resume something that can never work.
- fixed: `bruteforceLockout enable --threshold`/`threshold <N>` panicked
  (unhandled `ParseIntError` on `.unwrap()`) on a value too large for
  `u32`, instead of the same clean validation error every other bad
  value already got. Both call sites now share one `parse_threshold`
  helper that validates range, not just "digits only."
